# СЕТ — защита облачной синхронизации, этап 5 (изолированная лаборатория)

Дата: 2026-11-09
Статус: экспериментальная ветка, **НЕ релиз**. Опубликованное приложение остаётся v1.3.12.

## Проверено на действующей серверной схеме (ТОЛЬКО чтение метаданных)

- Публичная RPC `save_setlog_state` передаёт управление внутренней функции `setlog_internal.save_setlog_state`.
- Она использует `auth.uid()`, проверяет ожидаемую ревизию и обновляет пользовательский JSON в транзакции с блокировкой строки.
- При несовпадении ревизий сервер возвращает `revision_conflict`.
- RLS-политики таблиц `setlog_user_data` и `setlog_user_snapshots` связывают доступ с `auth.uid()`.
- Серверные данные, настоящие аккаунты, схема, права, таблицы и записи не изменялись.

Важно: в подключённом Supabase обнаружен **только рабочий проект** `setlog`. Отдельного испытательного проекта нет. Поэтому **реальных тестовых аккаунтов в рабочем Supabase не создавали**, RPC в рабочую базу не отправляли.

## Что сделано в приложении (изолированный тестовый режим)

- Использован настоящий код `syncCloudState`, `chooseCloudData`, `chooseLocalDataForCloud` и `applyCloudPayload`, но вместо реального SDK к нему подключён тестовый транспорт через `?atomicLab=1&atomicCloudLab=1`.
- Тестовый транспорт доступен **только если автоматизированный браузер его установил**. Он не содержит рабочих ключей и не обращается к серверу Supabase.
- Облачная версия сохраняется только из подтверждённого состояния IndexedDB.
- После загрузки облачной копии её локальное применение дожидается подтверждения IndexedDB, до показа успешного статуса.
- Если сервер принял запись, но ответ пропал, повторная попытка сверяет содержимое удалённого дневника. При полном совпадении безусловное «конфликт» заменено подтверждением уже совершённой записи.
- При новых локальных изменениях во время отправки первой версии не показываем «всё сохранено», пока не дойдёт последняя версия.
- Запросы имеют ID поколения, поэтому поздние ответы старого сеанса после выхода/повторного входа не изменяют новый сеанс и не блокируют новую отправку.

## Автоматические испытания

На двух независимых контекстах Chrome, разделяющих один искусственный RPC-сервер:

1. Два устройства сохраняют разную программу: первое побеждает, второе получает `revision_conflict`; локальная копия второго сохранена.
2. Пользователь выбирает версию сервера: она подтверждается IndexedDB, локальное состояние заменяется только после резервирования.
3. Пользователь выбирает локальную версию: старая серверная сохранена как резервная, после подтверждения новая версия попадает на сервер.
4. Сервер принял обновление, но ответ потерялся: повторное обращение узнаёт уже сохранённые данные.
5. Редактирование без интернета: подтверждённый локальный дневник дожидается восстановления связи и затем загружается.
6. Выход из аккаунта во время запроса: поздний ответ не возвращает прошлый сеанс.
7. Старый RPC завис, пользователь подключился заново: новый сеанс может синхронизироваться независимо, старый ответ игнорируется.
8. Две локальные правки во время первой облачной отправки: обе доставляются в правильном порядке, только последняя версия считается полностью синхронизированной.
9. Проверка изоляции фиктивных пользователей на имитированном сервере.
10. Прежние проверки операций, истории, импорта, восстановлений, экспорта PNG/PDF, Прогресса 2.0 и офлайна.

## Что пока НЕ доказано

- Это **не** полноценное E2E с настоящими Supabase Auth, JWT, PostgREST, реальным сетевым соединением и политиками доступа. Для него нужен отдельный sandbox Supabase или специально созданные фиктивные пользователи после дополнительной изоляции.
- Настоящие логин/логаут, смена аккаунта на устройстве, выбор локального дневника при первом входе и аварийный возврат данных из реального Supabase ещё не связаны с новым транзакционным хранилищем.
- Не проверены iOS Safari/PWA, принудительное закрытие приложения и ограничение памяти на телефоне.
- Полный аудит всех старых синхронных операций и финальная обратимая миграция всё ещё необходимы.

**НЕ сливать в main, не выпускать для пользователей.** Прежде чем подключать реальные данные, экспортировать JSON дневника и сохранить точку отката.

Локальное тестирование: `http://127.0.0.1:18788/?atomicLab=1&atomicCloudLab=1`.
Сам по себе этот адрес не подключит имитацию облака: её программно передаёт только браузерный тест `tests/atomic-cloud-multidevice.test.cjs`.
Для ручного просмотра местного дневника используйте `?atomicLab=1`.
