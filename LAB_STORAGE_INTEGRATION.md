# СЕТ · интеграция транзакционного журнала — эксперимент

**Статус:** рабочая тестовая ветка, не релиз. Ветка work/storage-atomic-integration. Основной сайт остаётся на v1.3.12.

## Что реально внедрено

- Настоящие экраны приложения (выбор тренировок, подходы, черновики, завершение тренировки) работают с новым транзакционным журналом через флаг atomicLab=1.
- Старый localStorage остаётся основным источником, а проверенная копия создаётся в независимой IndexedDB.
- Запись в IndexedDB — compare-and-swap с номером версии; предыдущее состояние записывается в той же транзакции.
- Web Locks не позволяет одновременно открытым тестовым вкладкам обеим стать записывающими. Вторая вкладка получает защитную заставку.
- При расхождении локального дневника и IndexedDB новая запись блокируется; исходники не перезаписываются. Можно скачать обе копии.
- Журнал хранит не больше 4 резервных версий для аккаунта.
- В режиме atomicLab=1 Supabase не инициализируется. Все тренировки тестовые, на отдельном локальном адресе. Приложение без флага работает по-старому.

## Как посмотреть

На компьютере с Desktop Commander: http://127.0.0.1:18784/?atomicLab=1
Это отдельный порт от опубликованного СЕТ, ничего не импортирует из боевого сайта.
Для самостоятельного запуска: python -m http.server 18784 --bind 127.0.0.1

## Проверки

- Ввод реального веса и повторов в интерфейсе, завершение и архивирование тренировок.
- Проверка сохранения черновиков и неизменности исторических записей.
- Конкурирующие вкладки: вторая не получает право записи до закрытия первой.
- Ревизии, четыре откатных копии, отказ от неизвестной/повреждённой версии.
- При разошедшихся источниках обе копии сохраняются и доступны для скачивания.
- Нет обращений к Supabase API в тестовом режиме.
- Обычные тесты истории, импорта, резервных копий, PNG/PDF и аналитики продолжают работать.

## Почему это ещё НЕ атомарная миграция боевого приложения

В тесте localStorage ещё обновляется раньше подтверждения транзакции IndexedDB. Поэтому нельзя говорить о полноценном атомарном сохранении двух хранилищ или включать режим всем пользователям. Кнопка может успеть подтвердить локальное сохранение, а журнал позже сообщить об ошибке.

Также не адаптированы прямые записи при смене облачного аккаунта, восстановлении серверной версии и импорте/экспорте в работающую синхронизацию. iOS Safari и фоновые ограничения PWA ещё не проверены. Никаких изменений схемы Supabase не выполнялось.

## Следующий этап до публикации

1. Сделать IndexedDB авторитетным хранилищем при сохранении с подтверждением транзакции перед уведомлением об успехе.
2. Адаптировать существующие синхронные вызовы persist и операции импорта, выбора аккаунта и восстановления облака.
3. Мигрировать предыдущий localStorage для каждого аккаунта с резервным снимком и обратимой процедурой.
4. Протестировать offline, quota, смену аккаунта, одновременные устройства, закрытие PWA посреди записи и Safari.
5. Сохранить отдельные update-only/full-restore ZIP, дать пользователю экспортировать JSON до переключения и выпускать только после зелёного CI.
