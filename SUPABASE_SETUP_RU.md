## 2. Важное ограничение исходящей почты Supabase

Стандартный встроенный SMTP в Supabase предназначен для тестирования и по умолчанию **отправляет письма только на адреса, относящиеся к членам команды проекта/организации**. Поэтому твой адрес может сработать, а друзья могут не получить письмо подтверждения или сброса пароля.

Чтобы друзья могли регистрироваться с подтверждением email, настрой отдельный SMTP-провайдер в [Auth → SMTP Settings](https://supabase.com/dashboard/project/xikwzwqorwdhwhurzmlx/auth/smtp). Не добавляй друзей в команду Supabase только ради писем: членство в организации даёт доступ к панели управления, а не просто к приложению. Не отключай подтверждение email ради обхода проблемы без осознанного решения.

## 3. База данных

Схема уже применена в проекте и проверена. Файл `supabase-setup.sql` прилагается как воспроизводимая миграция и сделан идемпотентным для этой версии. Повторно запускать его сейчас не нужно. Он не удаляет пользовательские данные, но при дальнейших изменениях схемы сначала создай отдельную контрольную точку.

В таблице хранятся пользовательские данные отдельной строкой на `auth.users.id`. Политики SELECT/INSERT/UPDATE ограничивают доступ строкой, у которой `user_id = auth.uid()`. У роли `authenticated` нет разрешения DELETE для текущего дневника. Обе функции работают как `SECURITY INVOKER`, не обходят RLS и проверяют владельца записи.

## 4. Публикация GitHub Pages

1. Перед загрузкой скачай резервную копию дневника из приложения и сохрани её отдельно.
2. Скачай архив обновления текущей версии и распакуй его.
3. Загрузи все файлы из корня распакованного архива в корень репозитория `sktkuzma/setlog`, заменяя одноимённые файлы.
4. Выполни один `Commit changes` в ветку `main` и дождись публикации GitHub Pages.
5. Открой `https://sktkuzma.github.io/setlog/` онлайн, зайди в раздел аккаунта и зарегистрируй свой аккаунт.

## 5. Перенос локальной истории

Если на устройстве уже есть история, изменённые программы, пользовательские упражнения или картинки, приложение должно показать экран выбора источника. Для первого аккаунта выбери перенос локальных данных в облако, если именно эта локальная копия актуальна. Перед переносом обязательно сохрани резервную копию отдельно от телефона.

Проверь, что после синхронизации сохранились обе программы, история, веса, повторы, картинки и ссылки. Затем открой приложение на втором устройстве и войди под тем же аккаунтом. Для проверки изоляции создай отдельный тестовый аккаунт и убедись, что он не видит данные первого.

## 7. Облачные сохранения

В аккаунте доступна кнопка «Предыдущие сохранения». Приложение хранит до 50 последних облачных копий. Копии создаются при изменении программы, истории тренировок или личной библиотеки; для черновиков частота ограничена — не чаще одного раза в 15 минут без других значимых изменений. Перед ручной заменой или восстановлением текущая облачная копия сохраняется отдельно.

Для новых аккаунтов первая копия создаётся при первой облачной записи. Для двух уже зарегистрированных аккаунтов начальные копии созданы.

## 8. Резервные копии и Free

Free не заменяет независимую резервную копию базы. Скачивай резервную копию дневника из приложения и периодически сохраняй независимую копию облачных данных отдельно. Не храни единственную копию данных только в телефоне или только в облаке.


### Облачные копии предыдущих состояний

После обновления приложение сохраняет до 50 предыдущих облачных состояний для каждого аккаунта. Обычные правки черновиков не создают отдельную копию при каждом нажатии: новая копия создаётся при изменении истории тренировок или структуры программ, а также не реже одного раза в 15 минут при продолжительной работе. Копии доступны в аккаунте приложения через кнопку «Предыдущие сохранения».

### Исправление сохранения облачных копий

В рабочей функции `public.save_setlog_state(jsonb, bigint)` устранена неоднозначность `revision` в обработке `ON CONFLICT`: используется ограничение `setlog_user_snapshots_user_revision_unique`. Исправление уже применено к рабочей базе и подтверждено тестовым сохранением. Файл `supabase-setup.sql` в актуальном пакете содержит ту же правку. Для обновления СЕТ 1.1.0 повторно запускать SQL не нужно.


## Восстановление пароля в версии 1.2.0

Для письма восстановления Supabase Auth возвращает пользователя в приложение по адресу `https://sktkuzma.github.io/setlog/`. Этот адрес должен быть добавлен в Supabase → Authentication → URL Configuration → Redirect URLs. Если адрес не разрешён, Supabase отклонит перенаправление. После публикации обязательно проверь полный сценарий на тестовом аккаунте: запрос письма, переход из письма, задание нового пароля и повторный вход. Схема базы и SQL для этого сценария не меняются.
